  * **RULE**: Dependencies must respect the declared architectural direction (inward towards Domain).
  * **RATIONALE**: Prevent circular dependencies and protect domain logic from infrastructure volatility.

* **AP-002 — Domain Isolation**
  * **RULE**: `core/domain` must not depend directly on infrastructure (`fs`, `child_process`).
  * **RATIONALE**: Ensure domain logic is pure and independently testable without I/O.

  * **TEST**: `phase-3-1-4-architectural-boundary.test.ts`

* **AP-005 — Storage Responsibility**
  * **RULE**: Storage persists and retrieves state; it must not fabricate domain conclusions.
  * **RATIONALE**: Business logic belongs to Engines and Rules.
  * **SOURCE**: `core/storage`

## 3. Causal Contract
The fundamental flow of execution is strictly progressive:
`Observation` → `Evidence` → `Fact` → `Finding` → `Resolution`

* **MANDATORY**: Each transition must preserve causality.
* **FORBIDDEN**:
  * `NO EVIDENCE` ≠ `VERIFIED`. Observation without evidence cannot lead to VERIFIED.
  * `NO_FINDING` ≠ `VERIFIED`. The absence of findings without evidence yields NOT_VERIFIED.
  * `SYNTHETIC EVIDENCE` ≠ `VALID PROOF`. Fabricated evidence cannot be used to pass governance constraints.

## 6. Dependency Contract
Allowed and Forbidden dependencies observed during Phase 3.1.4.
* **ALLOWED**:
  * Application → Domain, Engines, Storage, Collectors
  * Engines → Domain
  * Storage → Domain
  * Collectors → Infrastructure
  * Adapters → Infrastructure
  * Tests → System
* **FORBIDDEN**:
  * `core/domain` → `fs`, `path`, `child_process`
  * `core/domain` → `core/storage`, `core/adapters`
  * Rules → Raw infrastructure
  * Storage → Business decision engines
**AUTHORITY**: `scripts/check-architectural-drift.ts` enforcing these rules.

## 7. Trust Boundary
* **TRUSTED**:
  * Node.js runtime integrity
  * Host filesystem semantics
  * Process memory integrity
  * Local execution environment
  * Source tree integrity prior to execution
* **OUT OF SCOPE**:
  * Root compromise
  * Kernel compromise
  * Runtime memory tampering
  * Remote attestation
  * External independent oracle
  * Absolute cryptographic authenticity

## 8. Security Language Contract
* **PROHIBITED**: `ABSOLUTE IMMUTABILITY`, `ABSOLUTE AUTHENTICITY`, `ROOT-PROOF`, `TAMPER-PROOF`, `INDEPENDENTLY VERIFIED`.
* **ALLOWED**: `VERIFIED WITHIN TRUST BOUNDARY`, `PARTIALLY VERIFIED`, `SELF-GOVERNANCE`, `OUT OF SCOPE`.

## 12. Verdict Semantics
* **VERIFIED**: Produced by Engines/Quality Gate when execution succeeds with material evidence. Proves strict compliance within the Trust Boundary. Does NOT prove absolute root-proof security.
* **NOT_VERIFIED**: Produced by Engines when evidence fails requirements or is absent. Proves lack of compliance.
* **BLOCKED**: Produced by Governance Gates. An execution abort preventing further verification.
* **REJECTED**: Produced by early orchestrators when input context, provenance, or identity is invalid.
* **PARTIALLY_VERIFIED**: Conforms to some but not all constraints.
* **OUT_OF_SCOPE**: The property cannot be proven within the current Trust Boundary.

## 13. Self-Governance
* **SELF-GOVERNANCE ≠ INDEPENDENT ASSURANCE**.
* EOS can demonstrate consistency of its governance mechanisms according to its own controls.
* EOS cannot declare independence of those controls using only those same controls.

## 15. Contract Versioning
* **MAJOR**: Incompatible architectural change.
* **MINOR**: New compatible rule.
* **PATCH**: Documentation correction without semantic change.
A critical architectural change cannot be masked as PATCH. Any change to the contract must be classified (Class A/B) and validated via Governance Gates.
